## 1. Diagnostic — PREUVE PAR LES JOURNAUX TERRAIN (premier export du bouton v0.3.3)

L'export reçu (`nyx-logs-desktop-v0.3.3-20261027-152927.txt`) a objectivé la
cause racine RÉELLE — différente de tout ce qui avait été corrigé en v0.3.3 :

1. **Tor LUI-MÊME démarrait PARFAITEMENT** : le tor.log du terrain montre un
   bootstrap complet (consensus chargé, 2720 relais, circuits construits,
   garde primaire « moneybagg » en succès 25/25, keepalives netflow vivants)
   — le démon était un Tor parfaitement sain, orphelin de son contrôleur.
2. **Le client Java échouait en 16 à 62 millisecondes** : chronologie exacte
   du terrain — `tor.exe` lancé à 15:28:54.473, échec
   « control port : écriture impossible (ConnectException) » à 15:28:54.489
   (+16 ms), alors que Tor n'ouvrait son listener de contrôle qu'à
   15:28:54.569 (+96 ms). **Course du port de contrôle** : le connect TCP
   frappait un port pas encore ouvert → refused → backend FAILED.
3. **Le coupable : le cookie d'authentification PERSISTANT**. Tor n'efface
   jamais `control.authcookie` en quittant ; l'attente v0.3.3 « le cookie
   existe » passait donc INSTANTANÉMENT avec le fichier de la SESSION
   PRÉCÉDENTE, puis le connect ratrait le listener pas encore ouvert. Le
   retry tuait ensuite CE démon sain via killLeftoverTor — l'app se
   retrouvait FAILED avec, en mémoire, un Tor qui vivait très bien tout seul.
4. **Conséquence réplicas** : la sonde `/health` exige le SOCKS de Tor —
   backend FAILED = aucune sonde possible (« AUCUN — sonde impossible » dans
   l'export). Corriger Tor répare la chaîne réplicas.

## 2. Correctif connexion (cause racine, preuve à l'appui)

| # | Correctif | Détail |
|---|-----------|--------|
| 1 | **Purge du cookie périmé** | `purgeStaleCookie()` supprime `control.authcookie` AVANT chaque lancement — seul un cookie RÉGÉNÉRÉ par CE démon fait foi |
| 2 | **Attente d'un connect TCP RÉELLEMENT accepté** | l'ouverture exige désormais cookie frais ET `isPortOpen(control)` (connect éphémère 127.0.0.1, timeout 500 ms) — poll 250 ms, ≤ 60 s |
| 3 | **Journal de franchissement** | marqueur `nyx-tor` « control port ouvert (cookie régénéré + connect TCP accepté sur N) » — visible dans l'export de logs |
| 4 | **Tests de non-régression** | `isPortOpen` (port refusé = faux, listener ouvert = vrai) + purge du cookie périmé (DesktopStartupV4Test) |

## 3. Écran de connexion au démarrage — barre de progression (miroir ConnexionsScreen Android)

Demande opérateur : « au lancement, comme pour la version Android ». Portage
`ui/StartupConnectionScreen.kt`, mêmes libellés et même dynamique que
l'Android :

- **barre de progression GLOBALE** : Tor = moitié gauche (percent/2),
  réplicas = moitié droite (sonde /health) — formule miroir exact,
  testée JVM (`startupProgress`) ;
- **Étape 1 « Tor embarqué »** : pourcentage vivant + durée écoulée + indice
  de blocage (0 % > 60 s → « réseau filtré ? ») + bouton « Réessayer » si
  échec (message d'erreur complet de la bannière) ;
- **Étape 2 « Réplicas »** : sonde GET /health via Tor (boucle 8 s miroir
  ReplicaProbeEffect) — « en attente de Tor » puis sondage + bouton
  « Réessayer » manuel ;
- **auto-avance** quand les deux étapes sont vertes (petit délai 900 ms pour
  voir le vert — miroir Android) ; « Continuer sans attendre » garde l'app
  utilisable derrière (bannière Tor permanente) ;
- **carte ENVOYER LES LOGS** en bas de l'écran — c'est AU MOMENT d'un
  blocage ici que l'export sert.

## 5. Validation terrain (opérateur)

1. **Connexion au premier lancement** : la barre doit avancer (étape 1 Tor,
   pourcentage vivant) puis passer à l'étape 2 (réplicas) et OUVRIR
   l'application seule — plus d'échec instantané.
2. **Réseau coupé pendant le lancement** : échec lisible + « Réessayer » →
   rebrancher le réseau → le clic aboutit.
3. **Parité** : tester en priorité les vocaux 🎤 (les deux sens avec le
   téléphone), les pièces jointes, les mots de passe (panique = session
   leurre), la réduction au plateau (icône → la fenêtre revient), le plan de
   tests (chaque case cochée part dans les logs).
4. **Au moindre souci** : bouton rouge ENVOYER LES LOGS (sur l'écran de
   connexion OU dans la barre latérale) — le journal persistant emporte
   désormais les marqueurs « control port ouvert » et « nyx-test PASS ».
5. **Replicas** : si l'étape 2 reste rouge alors que Tor est prêt → coller
   l'onion d'un réplica vivant dans Réglages → Répliques personnalisés
   (la boîte de chaque contact accepté sert aussi d'amorçage automatique).
