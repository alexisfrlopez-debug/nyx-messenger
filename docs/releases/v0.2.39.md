# v0.2.39 (versionCode 43) — PRÉ-RELEASE

## Correctif principal — « toujours le problème \"SOCKS server failure\" et décrochage impossible »

Retour opérateur 22/10 soir (logs v0.2.38-test Xiaomi + v0.2.36-test
Blackview + console v0.8.6) : « toujours le problème \"SOCKS server
failure\" et décrochage impossible. la cause peut être la même, donc à
régler en priorité » — **l'opérateur a vu juste : cause IDENTIQUE des
deux symptômes, et elle se trouve dans le correctif v0.2.37 lui-même.**

### Cause racine — le HSFETCH de v0.2.37 était REJETÉ par tor (513)

Les trois logs le prouvent noir sur blanc, à CHAQUE tentative, sur les
DEUX téléphones ET la console :

```
HSFETCH vxb5tsk44i… échoué : control port : erreur Tor 513 — Invalid argument
```

v0.2.37 envoyait `HSFETCH <56 caractères>.onion` (62 caractères) alors
que le control-spec exige `HSAddress = 56*Base32Character` —
**l'adresse NUÈ, SANS suffixe `.onion`** (grammaire `"HSFETCH" SP
HSAddress` ; exemple officiel : `HSFETCH vww6ybal…pnpyyd` sans suffixe).
Vérifié dans le source tor 0.4.9.14 embarqué :

```
control_cmd.c  : handle_control_hsfetch → hs_address_is_valid(arg1)
                 sinon → « 513 Invalid argument "%s" »
hs_common.c    : hs_parse_address_no_log →
                 strlen(address) != HS_SERVICE_ADDR_LEN_BASE32 (56)
                 → « Invalid length » → invalide
```

Conséquence en chaîne : tor rejetait **100 % des HSFETCH** → la
récupération de descripteur n'a **JAMAIS opéré** sur le terrain → le
cache client a gardé les descripteurs périmés (points d'introduction
morts après chaque redémarrage d'app) → « SOCKS server general
failure » (échec d'INTRODUCE) en boucle → **appels acceptés mais sans
média** (« décrochage impossible ») + **réplica temporaire « SOCKS
injoignable »** dans la console. Les trois symptômes rapportés depuis
v0.2.36 ont cette origine commune.

### Correctif — l'adresse nue, des deux côtés, verrouillée par contrat

1. **Messager** (`TorControlClient.hsfetch`) : `HSFETCH <onion56>` —
   adresse nue de 56 caractères base32 (les appelants passaient déjà
   l'adresse nue ; seul le suffixe parasite était ajouté ici).
2. **Console v0.8.7** (miroir exact, `core/TorControlClient.hsfetch`) :
   même correctif — la sonde du réplica embarqué récupère enfin son
   descripteur.
3. **Tests de contrat réécrits** : le faux control port des tests
   VALIDE désormais l'adresse comme le vrai tor (250 si
   `^[a-z2-7]{56}$` exactement, **513 sinon**) — le test échoue par
   l'exception « erreur Tor 513 » si le suffixe `.onion` revenait.
   Le test v0.2.37 assertait la syntaxe… fausse (« avec suffixe
   complet ») : il verrouillait le bug au lieu de l'attraper — leçon
   retenue, un contrat doit encoder la SPEC, pas notre implémentation.

### Pourquoi ce fix suffit (chaîne vérifiée dans le source tor)

`handle_control_hsfetch` → `hs_control_hsfetch_command` →
`hs_client_launch_v3_desc_fetch` → fetch direct SANS le garde-fou
`can_client_refetch_desc` (donc même avec un descripteur « utilisable »
en cache) → `hs_cache_store_as_client` : le descripteur frais (révision
plus HAUTE) REMPLACE l'entrée périmée → la connexion SOCKS suivante
utilise les points d'introduction vivants → média d'appel établi,
sonde console OK.

### Détail terrain important — les DEUX téléphones doivent être en v0.2.39

Le test du 22/10 soir a été fait avec le Xiaomi en v0.2.38 (HSFETCH
présent mais rejeté 513) et **le Blackview resté en v0.2.36** (sans
HSFETCH DU TOUT — 11 tentatives média « SOCKS server general failure »
en salve, sans aucune récupération possible). Pour l'appel, c'est
l'APPELANT qui doit rafraîchir le descripteur de l'appelé : **les deux
appareils doivent être mis à jour** en v0.2.39 (installation
par-dessus, sans désinstaller).
