# v0.2.28 (versionCode 32) — PRÉ-RELEASE

Date : 2026-10-18
Base : v0.2.27 (d75e78e)

## Médias à vue limitée — style Instagram (demande opérateur)

« envoi de médias : je veux la possibilité d'afficher le media 1 fois puis
destruction du média, relecture autorisée 1 fois, ou affichage permanent ».

- **Choix AVANT l'envoi** : après le picking galerie/documents, un dialogue
  « Affichage du média » propose **Affichage permanent** (défaut) /
  **Vue unique** (détruit après affichage) / **Vue unique + 1 relecture
  autorisée**. La copie de l'expéditeur reste toujours relisible.
- **Transport** : champ `view` ajouté au JSON des fragments (chaque fragment
  porte la politique — crash-safe comme name/mime). **Rétrocompatible** : les
  fragments des clients v0.2.16-27 (sans le champ) sont lus « forever », et
  les anciens clients ignorent le nouveau champ (`ignoreUnknownKeys`).
- **Réception** : `attachments.viewPolicy` + `viewsLeft` (MIGRATION_9_10,
  Room v10 — 1 vue pour « once », 2 pour « twice »). La bulle du récepteur
  s'affiche **verrouillée** (« Toucher pour afficher — 1 vue, puis
  destruction ») ; chaque révélation consomme une vue ; à 0 vue le fichier
  local est **détruit** et la bulle affiche « média expiré ». Badge explicite
  (« vue unique » / « vue unique + 1 relecture ») des deux côtés.
- Garde-fou : valeur inconnue = « forever » ; l'expéditeur n'est jamais
  détruit chez lui ; la politique s'applique uniquement au récepteur.

## Compteur éphémère (demande opérateur)

« messages éphémères : j'aimerais un compteur à côté du message qui indique le
temps restant ». Chaque message à TTL (v0.2.26) affiche désormais sous la
bulle « éphémère : X min/h/j restantes » — horloge rafraîchie toutes les 30 s,
libellé humain (< 1 min / min / h / j).

## Interdiction des captures d'écran (demande opérateur)

« je veux interdire les captures d'écran dans l'application » — FLAG_SECURE
sur la fenêtre racine (MainActivity, inconditionnel, toute l'app : chats,
médias, appels, réglages) : captures d'écran et enregistrements d'écran
noirs, aperçu multi-tâches masqué.

## Appels — diagnostic renforcé (retour terrain « toujours impossible de
décrocher »)

Log v0.2.27-test2 (Blackview 12:17) analysé : chemin journal SAIN
(dépôt seq=76, inbox ✓, /health OK), AUCUNE tentative d'appel dans la fenêtre
capturée, et tor 0.4.9.14 renvoie « No more HSDir available to query » pour
un onion scrubé — la cause du décrochage impossible reste l'injoignabilité du
service onion du pair (descripteur non propagé / port média absent du
descripteur). v0.2.28 outille le diagnostic décisif :

- **Cible d'appel loguée** : chaque essai média journalise
  `nyx-call: média essai N → <onion préfixe>:47471` (le tor.log scrubbe les
  onions — le logcat app devient la trace exploitable).
- **Publication durcie** : l'ADD_ONION attend désormais (≤ 8 s) que l'écouteur
  P2P local soit lié AVANT de publier — un descripteur publié SANS le port
  média (race de démarrage) rendait tous les appels entrants morts jusqu'à la
  republication suivante ; cas logué explicitement.
- **SONDE AUTO** : 15 s après publication, l'app appelle SON PROPRE port média
  via le chemin onion complet — `nyx-p2p: auto-sonde média OK` = descripteur
  propagé et port servi ; `ÉCHOUÉE` = descripteur absent (cause racine
  « impossible de décrocher » visible DANS le log terrain, avec l'onion en
  prefixe).
