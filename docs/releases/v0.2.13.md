# v0.2.13 — L'identité survit aux relances (cause racine du blocage invitations)

**versionCode 17 · 2026-10-16 · APK standard + test (même keystore)**

## Retour terrain traité

> « logs envoyés, invitations toujours en attente »

Cette fois l'instrumentation v0.2.12 a parlé. Diagnostic sur les exports
v0.2.12 (051652 Blackview / 051654 Xiaomi) :

1. **Les deux téléphones échouent de la MÊME façon, toutes les 30 s** :
   - Blackview : `✗ annonce contact ÉCHOUÉE pour vxb5tsk44… : identité absente`
   - Xiaomi : `✗ annonce contact ÉCHOUÉE pour kxcwahchrto32… : identité absente`
     (×5 en 1 minute) + `→ msg peer=kxcwahchrto32… len=4` suivi immédiatement
     de `envoi signalé en échec à l'UI` — l'envoi de message échoue AUSSI.
2. **Pendant ce temps Tor publie l'onion sans problème** (`onion service
   publié : vxb5tsk…`, `GET /health OK`) : l'identité existe bien, elle n'est
   simplement pas chargée là où on la demande.

## Cause racine (présente depuis la v0.2.9 — fermée aujourd'hui)

Dans `IdentityManager`, `onionAddress` et `publicKey` étaient des champs
**mémoire uniquement**, remplis par `createIfNeeded()` — qui n'est appelé
QUE depuis l'écran d'onboarding. Après CHAQUE relance du processus
(fermeture de l'app, redémarrage du téléphone, crash de Tor), ces champs
restaient `null` jusqu'à un hypothétique re-onboarding :

- `send()` / `sendContactNotification()` / `sendContactAck()` / `claimAlias()`
  / `publishProfile()` → `identité absente` (échec immédiat, visible en
  v0.2.12+) ;
- `pollInbox()` → **silencieux** `return 0` : même si une invitation avait
  réussi à atteindre le réplica, personne ne la récupérait jamais ;
- `secretKey()` lisait directement les préférences → Tor publiait l'onion
  pendant que tout le reste échouait — d'où la contradiction des logs.

C'est LA cause unique du blocage constaté depuis la v0.2.9 : invitations
jamais reçues, messages jamais livrés, statuts figés « en attente ».
(L'alias, lui, avait déjà un getter adossé aux préférences — l'asymétrie
explique que le claim d'alias ait pu fonctionner après relance.)

## Correctif (client uniquement — serveur v0.2.0 INCHANGÉ)

- `IdentityManager.onionAddress` / `publicKey` : getters **adossés aux
  préférences** (pattern `alias`) — lecture des prefs au premier accès,
  mémoïsée ensuite. L'identité survit à toute relance sans dépendre de
  l'onboarding ; les 6 chemins touchés sont corrigés d'un seul coup.
- Aucune migration Room, aucun changement de wire-format, aucun changement
  serveur. Version bump 16 → 17.

## Pourquoi l'e2e ne l'avait pas attrapé

Les scripts e2e (e2e_repro.py, e2e_v0212.py) testent le serveur Go avec des
clients Python : ils ne peuvent pas voir un état mémoire Android. Le trou de
couverture (persistance IdentityManager à travers un relance de processus)
est documenté dans RESTART.md — il nécessiterait un test instrumenté Android
(roadmap, pas bloquant : le correctif est une lecture de prefs).

## À tester (les 2 téléphones, mise à jour directe par-dessus v0.2.12)

1. Installer v0.2.13 sur les DEUX téléphones, ouvrir l'app, laisser ~1 min.
2. Xiaomi : l'invitation « en attente » doit passer le cycle (log
   `✓ annonce déposée`) et Blackview doit voir la carte d'invitation
   (boutons Accepter / Refuser).
3. Accepter sur Blackview → Xiaomi voit « … a accepté votre invitation. »,
   le statut passe à acceptée (le libellé disparaît de la liste).
4. Envoyer un message dans les deux sens → visible immédiatement côté
   expéditeur ET reçu côté destinataire (~30 s max, poll global).
5. Fermer complètement les deux apps, relancer, renvoyer un message → doit
   partir sans « identité absente » (c'est le cas qui fermait tout depuis
   la v0.2.9 — désormais impossible).
