# Nyx v0.2.5

## Écran CONNEXIONS en première page (Tor → Réplica), bouton rouge sur cet écran

Demande opérateur : « Il faudrait que la première page qui s'affiche soit celle
des connexions, avec une barre de progression : TOR puis Replica, avec bouton
d'envoi de logs sur cette page aussi pour la version test. Une fois les étapes
de connexion validées, on peut afficher le reste. »

## Nouveau flux de démarrage

- **Écran Connexions = porte d'entrée unique** (`ui/connexions/ConnexionsScreen`) :
  affiché À CHAQUE lancement, avant l'onboarding ET avant les conversations.
  - Étape 1 — **Tor embarqué** : pourcentage de bootstrap en direct (poll du
    control port, 1 s), durée écoulée, « Prêt » en vert, bouton « Réessayer »
    en cas d'échec (relance propre stop+start du démon).
  - Étape 2 — **Réplica d'amorçage** : sonde GET /health via Tor, répétée
    toutes les 8 s, détail d'erreur affiché sous la barre (HTTP code ou
    exception), bouton « Réessayer » pour court-circuiter l'attente.
  - **Barre de progression globale** : Tor = moitié gauche (0–50 %),
    réplica = moitié droite (50–100 %), avec libellé « Étape x sur 2 ».
  - **Auto-avance** : les deux étapes validées → le reste de l'app s'affiche
    automatiquement (onboarding si aucune identité, conversations sinon),
    après un court délai pour laisser voir le vert.
  - Alerte dédiée si Tor reste à 0 % plus d'une minute (piste réseau filtré,
    conseils de changement de connexion) — cas Blackview v0.2.4.
- **Bouton rouge SUR la page connexions** (build test uniquement) : le gros
  bouton d'export des logs vers le dossier de travail Drive est désormais
  présent à l'endroit exact où l'app peut rester bloquée. Les emplacements
  existants (onboarding, conversations) sont conservés.

## Correctifs de diagnostic (logs device v0.2.4)

- **Sonde réplica muette — corrigé** : dans l'onboarding, la boucle de sonde
  était clé sur l'état Tor COMPLET (`LaunchedEffect(torState)`) — chaque tick
  de pourcentage pendant le bootstrap relançait l'effet et ANNULAIT la requête
  en vol avant tout résultat. La boucle est extraite dans
  `ui/components/ReplicaProbeEffect` (unique copie, audit RED-DUP) et clé sur
  le SEUIL Ready/pas-Ready.
- **Échecs de sonde loggés** (`RelayClient.healthDetailed`, tag `nyx-conn`) :
  les exceptions étaient avalées (`getOrDefault(false)`) — « réplica
  injoignable » ne laissait AUCUNE trace. Chaque tentative logue désormais
  durée + cause (HTTP 50x, ConnectException, SocketTimeout…), et le rapport
  complet est exposé à l'UI (`NyxRepository.lastProbe`).
- **Bootstrap Tor logué** (`TorManager.watchBootstrap`, tag `nyx-tor`) : chaque
  palier de pourcentage est logué — les « Bootstrapped X% » natifs vont dans
  tor.log (torrc « Log notice file ») et NON dans logcat.
- **tor.log embarqué dans l'export** (`LogCollector`) : la FIN de
  `files/tor/tor.log` (256 Ko max) est ajoutée à l'export du bouton rouge,
  ainsi que la liste des réplicas d'amorçage embarqués dans l'en-tête. Un Tor
  bloqué à 0 % est désormais démontrable depuis un export (cas Blackview).

## Divers

- Scaffold partagé `ui/components/ScreenColumn` (l'audit RED-DUP interdit les
  copies divergentes) ; boucle de sonde unique `ReplicaProbeEffect`.
- `TorManager.retry()` : relance propre (stop tue le démon via onDestroy,
  start relance un démon frais) — un simple `start` ne suffit pas quand le
  process tor existe déjà (NyxTorService ne re-déclenche pas reportStarted).
- versionCode 9, versionName 0.2.5 / 0.2.5-test.
- Côté serveur : aucun changement.
