# v0.2.47 (versionCode 51)

## « Oignon entrant injoignable » + « décrochage impossible » : UNE seule ligne fautive depuis le début — le bind des écouteurs sur ::1 au lieu de 127.0.0.1 (session 69)

Demandes opérateur (sessions 67-68, toujours d'actualité) : « je veux réglé le
probleme "oignon entrant injoignable" qui apparait sur les replicas embarqués
dans la console » / « serait-il possible que le problème récurrent de
décrochage d'appels impossible soit lié ? (c'est toujours le cas
actuellement) ».

### La cause racine, PROUVÉE par le source AOSP + les logs du 24/10

`InetAddress.getLoopbackAddress()` **ne retourne PAS 127.0.0.1 sur Android**.
Le code source AOSP (libcore/ojluni `java/net/InetAddress.java`) :

```java
public static InetAddress getLoopbackAddress() {
    // Android-changed: Always returns IPv6 loopback address in Android.
    return impl.loopbackAddresses()[0];   // ← ::1 — JAMAIS 127.0.0.1
}
```

Les DEUX écouteurs locaux (réplica embarqué `EmbeddedReplica`, média P2P
`P2pServer`) bindaient `[::1]:<port>` depuis leur création, alors que
l'ADD_ONION publie `Port=…,127.0.0.1:<port>` — **tor a donc TOUJOURS reçu
« Connection refused »** (errno 115 → END misc → « SOCKS server general
failure » chez tous les pairs) sur des backends vivants et sains. Sur le JVM
desktop (bac à sable, tests), la même méthode retourne 127.0.0.1 : voilà
pourquoi TOUTES les validations sandbox passaient alors que AUCUN téléphone
n'a JAMAIS accepté une seule connexion entrante — de la v0.2.18 (P2P) et
v0.2.19 (réplica embarqué) à la v0.2.46.

### La boucle de mort du chien de garde (v0.2.45) : un faux positif à 60 s

Les exports du 24/10 05:21 (Blackview v0.2.45) et du 23/10 23:27 (Xiaomi
v0.2.45) montrent la même boucle strictement périodique, toute la nuit, sur
les DEUX téléphones :

```
réplica prêt (local 38825) → 45 s → réplica MORT (38825 « refuse »)
  → relance (46133) → republication onion → 60 s → MORT → …
```

45 « écouteur interrompu : Socket closed » dans un seul export, un « écouteur
direct prêt » **en double** à 1 ms d'écart (race chien de garde ↔
auto-guérison P2pServer — socket orphelin), un descripteur onion republié
toutes les 60 s (churn HSDir permanent). La sonde `alive()` interroge
`127.0.0.1` — adresse où le backend n'existe pas — donc verdict MORT sur un
backend parfaitement vivant sur `[::1]`. Le chien de garde v0.2.45 faisait
son travail sur de fausses données : il ne pouvait QUE relancer en boucle.

### La réponse définitive à la question de l'opérateur : OUI, même cause

- **« Oignon entrant injoignable » (console)** : la sonde directe de la
  console passe par l'onion du téléphone → tor → `127.0.0.1:<port>` →
  REFUSED. Le réplica embarqué n'a JAMAIS été joignable en direct — la
  console voyait juste, et NYX-LINK (v0.2.46) masquait le symptôme par le
  canal sortant.
- **« Décrochage impossible » (appels)** : le média direct exige l'onion
  ENTRANT du pair (`:47471`) → backend du pair sur `::1` → REFUSED → l'audio
  ne s'établit JAMAIS. Le repli relais v0.2.44 (par le réplica de flotte,
  lui en Go, bind correct) peut fonctionner dès que le serveur de flotte est
  en 0.2.36+ — d'où les décrochages partiellement fonctionnels parfois
  observés APRÈS le déploiement 0.2.36, jamais avant.

Un seul bug, deux symptômes. La corrélation suspectée par l'opérateur était
exacte — et elle est PLUS profonde que le lien signalisation/média documenté
en v0.2.46 : c'est la MÊME ligne fautive.

### Les correctifs

1. **`net/Loopback.kt` (nouveau)** — helper unique de bind loopback :
   `InetAddress.getByName("127.0.0.1")` explicite (littéral IP, aucune
   résolution), documentation intégrée du piège AOSP, contrat verrouillé par
   test. RÈGLE : tout écouteur mappé sur l'onion passe par `Loopback.serverSocket()`.
2. **`EmbeddedReplica.start()`** — bind via `Loopback.serverSocket(16)` ;
   le journal « prêt » affiche désormais l'adresse (`local 127.0.0.1:PORT`)
   pour preuve terrain immédiate.
3. **`P2pServer.start()`** — même bind IPv4 explicite + **garde de
   propriété `selfHealIfStillOwner`** : l'auto-guérison du thread d'écoute ne
   relance PLUS un écouteur si le socket mort n'est plus celui publié
   (la race avec le close du chien de garde créait le double « prêt » —
   terrain 24/10 05:22:38, ports 42899/44763, socket orphelin + churn).
4. Les chiens de garde, HSFETCH de guérison, NYX-LINK, relais média et
   Detach serveur sont inchangés — ils deviennent enfin UTILES au lieu de
   courir après un fantôme d'adresse.

  relais à 60 s.
