# v0.2.22 — réparation du schéma Room (crash-loop au démarrage)

**versionCode 26 · 3 APK (standard / test / test 2) · correction commune à TOUTES les versions**

## Le problème (retour terrain, logs 11:50)

Après installation de v0.2.21-test par-dessus une version antérieure, l'application
**Nyx TEST crashait en boucle juste après la connexion au relais réplica** :

```
FATAL EXCEPTION: main
java.lang.IllegalStateException: Migration didn't properly handle:
replica_events(net.nyx.messenger.data.db.ReplicaEventEntity).
```

Trois crashs en une minute (11:49:57, 11:50:40, 11:50:50) — l'appareil était
inutilisable : chaque ouverture de la base re-jouait la migration 6→7, la
validation Room rejetait le schéma, la transaction était annulée et le
processus mourait. Aucune donnée n'a été perdue : la base restait bloquée à
l'ancienne version, en boucle.

## La cause

La migration **6→7** (v0.2.19, réplica temporaire) crée la table
`replica_events` **avec un index inbox** `index_replica_events_to_gid` sur
(`to`, `gid`) — mais l'entité Room `ReplicaEventEntity` **ne déclarait pas cet
index**. Conséquence, deux populations d'appareils divergentes :

- **Mise à niveau 6→7** (ex. Blackview, v0.2.18 → v0.2.21) : la table porte
  l'index → la validation Room rejette le schéma → **crash en boucle** ;
- **Installation fraîche v7** (v0.2.19+) : la table est créée SANS index →
  validation OK (c'est pourquoi certains appareils n'ont pas crashé).

Le bug a été introduit en v0.2.19 et ne s'est manifesté qu'à la première mise
à niveau réelle 6→7 sur le terrain.

## Le correctif (zéro donnée détruite, convergence de tous les chemins)

1. **L'entité déclare désormais l'index** (`Index(value=["to","gid"], name=
   `index_replica_events_to_gid`)`) — nom explicite = nom canonique Room :
   le schéma attendu redevient identique au schéma migré.
2. **Base version 8 + MIGRATION_7_8** : `CREATE INDEX IF NOT EXISTS` — no-op
   pour les bases déjà migrées (index présent), crée l'index pour les bases
   d'installation fraîche v7 (sans index). Migrés 6→7→8, fraîches v7→8,
   fraîches v8 : **tous les chemins convergent vers le même schéma**.
3. Les bases leurre (mot de passe panique) suivent le même schéma : rien à faire.
4. Constantes partagées entité/migration (`INDEX_REPLICA_EVENTS_TO_GID`,
   `SQL_INDEX_REPLICA_EVENTS_TO_GID`) — une seule source de vérité.

## Garde anti-régression (NyxSchemaGuardTest, +8 tests JVM)

Les annotations Room étant en rétention CLASS (invisibles par réflexion JVM),
le test capture le **DDL réellement généré par Room** (`NyxDatabase_Impl`,
classe KSP générée) et vérifie :

- le DDL de création fraîche contient **exactement un index**, celui de
  l'entité (si l'index disparaît de l'entité, le CREATE INDEX disparaît du
  DDL → échec de build) ;
- l'index créé par les migrations porte **le même nom** que celui de l'entité ;
- les trois tables v7 (del_pending, replica_events, replica_state) restent
  complètes dans le DDL ;
- la **version de la base** (lue via createOpenHelper rejoué) = 8 ;
- les bornes MIGRATION_6_7 / MIGRATION_7_8.

**111 → 119 tests JVM verts.** Audit PASSED (0 CRIT / 0 MAJOR). 13/13
contrôles d'autonomie × 3 APK (signature, Tor embarqué 4 ABI, natives
critiques, universel, permissions fermées, zéro GMS).

## Remarque sur les crashs « read interrupted by close() » (10-16, nuit)

Les 4 FATALE `InterruptedIOException` visibles dans le même tampon de logs
datent de la nuit du 10-16 — fenêtre **v0.2.10** (drain coroutine) : fermées
par v0.2.11 (drain sur thread démon), aucun crash de ce type depuis. Résidus
d'ancien tampon logcat, aucune action requise.
