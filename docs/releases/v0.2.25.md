## Contenu

### 1. TOR EMBARQUÉ : 0.4.6.5 (EOL) → 0.4.9.14 — LA CAUSE RACINE DES APPELS MORTS
- **Preuve dans les logs terrain** (tor.log 19:57:20-33) : `The missing
  protocols are: Desc=3-4 FlowCtrl=2 Microdesc=3 Relay=4-6` puis
  `Closed 1 streams for service [scrubbed].onion for reason resolve failed.
  Fetch status: No more HSDir available to query.` — le consensus Tor 2026
  requiert des protocoles que tor 0.4.6.5 ignore : le client ne peut plus
  interroger AUCUN HSDir → **aucune résolution onion « fraîche » possible**.
- **Conséquences exactes du terrain** : la signalisation d'appel (journal via
  réplica — descripteurs en cache) passait → ça SONNE ; mais le MÉDIA direct
  onion-to-onion (port 47471) exigeait de résoudre l'onion du pair →
  `Host unreachable` ×3 → l'appel mourait (décrochage sans effet) ; idem
  P2P fichiers (`Connect timed out`) → tout passait par le chemin journal
  (relais, séquentiel) → « un peu long ».
- **Correctif** : les 4 binaires `libTor.so` (arm64-v8a 0.4.9.14 = security
  release ; armeabi-v7a/x86/x86_64 0.4.9.13) extraits des APK officiels Orbot
  (guardianproject/orbot-android « fullperm »), placés dans
  `app/src/main/jniLibs/<abi>/` — remplacent la dépendance Maven
  `io.matthewnelson.topl-android:tor-binary:0.4.6.5` (EOL, dernière MAJ 2021).
  Provenance, SHA-256 et procédure de mise à jour : `jniLibs/README.md`.
  Choix justifié : gpmaven injoignable au poste, JitPack échoue (git clone) ;
  le binaire tor-android est « used directly as a tor daemon » (README
  Guardian) — comportement identique à l'ancien libTor.so topl, `NyxTorService`
  inchangé. Déps statiques vérifiées (libevent/openssl/zlib), minSdk 24 ≤ 26.

### 2. RÉPLICAS TEMPORAIRES AUTO-PARTAGÉS entre contacts (test 2)
- **Nouveau** : un appareil qui sert un réplica temporaire annonce
  `{"alias":…,"replica":"<onion>:80","ver":…}` à CHACUN de ses contacts
  acceptés — événement type « contact » chiffré E2E (**zéro changement
  serveur**, corps opaque, type standard du journal).
- **Réception** (ReplicaCodec + ReplicaRegistry) : garde-fous d'identité
  (l'adresse annoncée DOIT être celle de l'AUTEUR — on ne peut annoncer que
  SON propre réplica), ingestion **persistée** (7 jours sans ré-annonce) ;
  les réplicas découverts passent AVANT le rendezvous dans la fusion
  (custom > découverts > rendezvous > bootstrap) — « restent en mémoire pour
  accélérer les connexions suivantes » ; re-fusion appliquée SANS redémarrage
  à chaque annonce entrante.
- **Émission** : au premier tick Tor Ready puis toutes les 30 min tant que le
  réplica embarqué sert (ServiceLocator, boucle poll existante).
- **Compatibilité** : un client ancien qui reçoit le corps retombe dans
  « annonce déjà traitée » (aucun alias/ack → aucun effet, le champ « alias »
  garde le label lisible).

### 3. FAILOVER de réplicas (connexions suivantes robustes)
- **Avant** : `relay()` utilisait `replicas.firstOrNull()` — SI le premier
  réplica tombait (téléphone contact éteint), TOUT échouait (poll + dépôts)
  sans jamais essayer le suivant.
- **Après** : `markReplicaFailed()` (round-robin borné) sur échec de transport
  du poll inbox → bascule immédiate sur le réplica suivant ; l'auto-guérison
  tor (v0.2.17) ne se déclenche plus que si TOUS les réplicas échouent.

### 4. AUTO-AJOUT des réplicas à la console admin (côté serveur)
- Le champ public **« replica »** est ajouté à la carte de profil (whitelist
  §7.2 client + serveur) avec **garde-fou d'identité** : la valeur doit être
  « <author.onion>:<port 1-65535> » — un pair ne peut pas diffuser l'adresse
  d'un tiers (anti-relais d'adresses arbitraires).
- **Nouveau endpoint** `GET /admin/replicas` : agrège les dernières cartes
  publiques portant le champ (journal.Store.ReplicaAnnouncements, ré-annonce
  ≤ 7 jours, double vérification du garde-fou au scan) — la console nyx-admin
  alimente son onglet « Répl. embarqués » avec cette liste (AUTO-AJOUT, plus
  d'inscription manuelle). Branchement console : dépôt privé, session suivante.

### 5. Partage sans Drive : CLIPDATA (FB Messenger « fenêtre fermée puis rien »)
- **Cause** : la grant READ du `EXTRA_STREAM` n'est pas toujours propagée aux
  cibles À TRAVERS le ChooserActivity (apps exigeantes qui lisent l'URI hors
  process — FB Messenger) → refus silencieux, fenêtre fermée.
- **Correctif** : `ClipData.newUri` sur l'intent (mécanisme canonique : la
  permission recopiée pour CHAQUE cible), + `EXTRA_TEXT` court (résumé e-mail)
  + try/catch (un échec de launch affiche le motif au lieu du silence) +
  log `nyx-share` (diagnostic terrain).
