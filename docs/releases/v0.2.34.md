## LA CAUSE RACINE HISTORIQUE DES APPELS : ONION DÉTRUIT À LA NAISSANCE

Les exports terrain v0.2.33 (22/10, deux téléphones) ont fourni pour la
première fois la PREUVE COMPLÈTE du scénario d'échec grâce aux auto-sondes
et à l'anneau persistant :

```
10-22 09:07:42 I nyx-call: appel entrant de kxcwahchrto32cp3… (cid 107b9751…)
10-22 09:07:46 I nyx-call: acceptation utilisateur (cid 107b9751… — média pas encore arrivé)
10-22 11:07:35 I nyx-call: média essai 1 → vxb5tsk44ikklazo…:47471
10-22 11:07:47 I nyx-call: connexion directe impossible vers vxb5tsk44ikklazo… (Connect timed out)
```

La signalisation passe (sonnerie + décrochage — chemin journal via les
nœuds), mais le MÉDIA direct onion→onion ne s'établit JAMAIS : chaque essai
`média essai N → :47471` se termine en `Connect timed out` / `SOCKS: Host
unreachable`. Les auto-sondes des DEUX téléphones échouent sur les DEUX
ports (média 47471 ET réplica 80) dès 15 s après publication, et le tor.log
montre des fetchs `No more HSDir available to query` en boucle pendant des
heures — UNIQUEMENT pour les onions des téléphones, jamais pour ceux des
nœuds (messages reçus pendant tout l'épisode).

### Le mécanisme (documenté dans NOS propres sources)

`server/internal/tor/control.go` — bug v0.2.0 n°2, observé en production
côté serveur dès la v0.2.0 :

> « un service publié via ADD_ONION est ÉPHÉMÈRE — tor le détruit dès la
> fermeture de la connexion contrôle qui l'a créé (comportement observé :
> carte console rouge après quelques secondes). On ne ferme PLUS la
> connexion après publication : Watch() la maintient ouverte »

C'est EXACTEMENT pourquoi les nœuds sont joignables (le serveur Go garde
sa connexion contrôle ouverte en permanence) et pourquoi les téléphones ne
l'ont JAMAIS été : `TorManager.publishOwnOnion()` publiait via
`TorControlClient(...).use { … }` — le `.use {}` FERME la connexion
contrôle immédiatement après l'ADD_ONION → tor détruit le service dans la
seconde → le descripteur n'est jamais propagé → personne ne peut joindre
le téléphone. L'app, elle, affichait « onion publié » (l'ADD_ONION avait
réussi et l'adresse est restée constante — même clé).

Ce mécanisme unique explique TROIS symptômes rapportés depuis des
semaines :
1. **« Appels/visio ne décrochent pas »** — le média exige de joindre
   l'onion du pair : impossible, service mort.
2. **« Réplicas embarqués "sert" sur le téléphone mais absents de la
   console »** — le téléphone SERT bien localement, mais son :80 est
   injoignable de l'extérieur, et surtout les annonces lues par la console
   restaient vides (voir console v0.8.4 : nœud de prod < v0.2.25).
3. **`Host unreachable` / `No more HSDir available to query`** en boucle —
   le descripteur n'existe dans aucun HSDir.

### Correctifs

1. **`Flags=Detach,DiscardPK`** dans l'ADD_ONION
   (`TorControlClient.publishOnionEd25519V3`) : le service SURVIT à la
   fermeture de la connexion contrôle (spec control-port Tor). `DEL_ONION`
   reste fonctionnel depuis n'importe quelle connexion authentifiée —
   l'arrêt propre et la republication forcée du watchdog fonctionnent à
   l'identique.
2. **Sérialisation des publications** (`onionMutex` dans `TorManager`) :
   terrain 22/10 02:52:41 — trois connexions contrôle ouvertes LA MÊME
   SECONDE, deux ADD_ONION avec la même clé en concurrence →
   `tor_bug_occurred_` + `Onion Service private key collides with an
   existing v3 service` (551). Le publicationWatchdog, le probeWatchdog et
   l'annonce périodique peuvent tous vouloir republier : désormais un seul
   à la fois.
3. **Test de régression JVM** (`TorControlClientTest`, faux control port
   TCP) : fixe le contrat `Flags=Detach,DiscardPK` + les deux ports
   (80 + 47471) + `DEL_ONION` depuis une nouvelle connexion. Ce test
   aurait attrapé le bug avant TOUT le terrain.

## Console v0.8.4 (miroir) — découverte embarquée : plus d'échec silencieux

Terrain 22/10 (log console 09:06:55) : `[flotte] Transport XMPP MUC :
joignable` PUIS `[embarqué] découverte : 0 nœud(s) interrogé(s)` — le
nœud répond à `/admin/status` mais `GET /admin/replicas` échouait en
SILENCE (`?: continue` avalait l'exception). Cause la plus probable :
**le nyx-server de production (VM Oracle, transport XMPP) est antérieur à
la v0.2.25** (l'endpoint `/admin/replicas` et le champ « replica » des
profils publics ont été introduits en v0.2.25) → HTTP 404.

- v0.8.4 : chaque échec de `tempReplicas()` est journalisé AVEC la cause
  (desktop + APK) ; un 404 affiche « GET /admin/replicas absent (HTTP
  404) — nyx-server < v0.2.25 : METTRE LE NŒUD À JOUR » ; la version du
  nœud (`/admin/status`) accompagne le message.
- **Action opérateur requise** : redéployer le nyx-server courant sur le
  nœud de production (console → machine SSH → boîte à outils / déploiement
  1-clic) — sans cela, la découverte reste vide quel que soit le client.
