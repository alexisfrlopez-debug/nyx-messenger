# v0.2.43 (versionCode 47)

## Réplica embarqué injoignable dans la console — publication onion stabilisée (session 64)

Retour opérateur : « toujours problème de replica embarqué injoignable dans la
console à cause d'une défaillance socks. Il faut régler ce problème qui doit
être central à d'autres soucis rencontrés ».

### Diagnostic — expérimentation tor RÉELLE (nouvelle méthode)

Pour la première fois, la cause racine a été établie par **reproduction en
laboratoire avec un vrai démon tor** (bundle expert 0.4.8.17, scripts
`tor_repro_embedded.py` / `tor_repro_controls.py` / `tor_repro_final.py`,
conservés dans le workspace) :

1. **PREUVE** : `ADD_ONION ED25519-V3 Flags=Detach,DiscardPK` suivi de la
   FERMETURE de la connexion contrôle (le geste exact de l'app) laisse le
   service VIVANT — il établit ses points d'introduction et téléverse son
   descripteur : **47 réponses « 200 OK HS descriptor stored successfully »**
   en laboratoire. Le protocole de publication v0.2.34 est CORRECT.
2. **PREUVE (terrain)** : la collision 550 « Onion address collision » constatée
   en boucle dans les logs terrain (22-23/10) signifie « le service existe
   DÉJÀ dans CE démon tor » — donc il fonctionnait pendant que l'app croyait
   l'échec.
3. **Défaillance du client sandbox** (méthodologie) : le réseau du bac à sable
   ne peut FETCHER aucun descripteur (même torproject.org renvoie « Host
   unreachable ») — la joignabilité côté client reste donc instruite par les
   seuls logs terrain.

### Cause racine applicative — 3 bugs en chaîne dans les watchdogs

**(1) Double enveloppe `Result` = gestion de collision MORTTE (v0.2.37 → v0.2.42).**
`runCatching { publishOwnOnion() }` enveloppait une fonction qui renvoie DÉJÀ
un `Result` : la branche `.onFailure` (adoption « collision = service déjà
vivant ») était **INATTEIGNABLE**. Preuve terrain : « onion service publié :
Failure(…550 collision…) » journalisé via la branche SUCCÈS (23/10 09:12:56).

**(2) Collision 550 traitée en échec → boucle de republication sans fin.**
Chaque collision laissait `onionPublishedAddress` à null alors que le service
était vivant → le publicationWatchdog re-ADD toutes les 30 s → nouvelle
collision → à jamais « non publié » + assertion interne tor
(`hs_service_add_ephemeral`) à chaque tentative.

**(3) Dernier recours DEL+ADD destructeur.** Après 4 salves de sonde en échec,
le probeWatchdog DEL_ONIONnait le service (tuant des points d'introduction
VIVANTS), rouvrait une fenêtre de descripteur périmé pour tous les pairs, puis
courait contre le publicationWatchdog (collision 550). Sur réseau mobile, ce
churn empêchait la stabilisation des descripteurs.

**Contribution aggravante** : l'auto-sonde du téléphone sur SA PROPRE onion est
faussée par le cache client tor (jusqu'à 24 h) qui sert l'ANCIEN descripteur
(points d'intro d'une session précédente) → « SOCKS server general failure »
est un FAUX NÉGATIF connu, pas une panne réelle — il déclenchait pourtant
toute la cascade (3).

### Correctifs

- **Adoption de collision** : `publishOwnOnion` reconnaît la 550 collision et
  ADOPTE le service existant (même clé = même adresse ; même écouteurs dans le
  processus). Cas particulier : si l'enregistrement existant date d'une
  publication SANS port média et que l'écouteur P2P est maintenant lié, un
  rafraîchissement propre DEL+pause+ADD est fait (mutex sérialisé, aucune
  course possible).
- **Fin du double `Result`** : les deux watchdogs consomment directement le
  `Result` de `publishOwnOnion` — les branches d'échec redeviennent vivantes.
- **Fin du dernier recours destructeur** : plus AUCUNE republication forcée
  déclenchée par les sondes ; 4 salves persistantes malgré HSFETCH produisent
  une ALERTE JOURNALISÉE explicite (tor re-téléverse ses descripteurs et
  ré-établit ses points d'intro en autonomie). Les canaux SORTANTS (réplication,
  appels sortants, annonces) restent fonctionnels même quand l'onion ENTRANT
  est injoignable.
- **Sonde indicative + classification honnête** : « SOCKS server general
  failure » = descripteur servi mais INTRODUCE en échec (cache 24 h / points
  d'intro morts) ; « Host unreachable » = aucun descripteur servi par les
  HSDirs. Les textes d'explication erronées (« descripteur probablement jamais
  propagé ») sont retirés.
- **Hygiène tor-data (état guards)** : le fichier `state` du DataDirectory
  tor est réinitialisé à chaque changement de version d'app — terrain 22-23/10 :
  « All current guards excluded by path restriction type 2 » dès la PREMIÈRE
  seconde de chaque bootstrap (exclusions accumulées persistées par le réseau
  mobile, sans cesse re-mémorisées).

### Réponse à la question du canal de secours P2P pur

Demande : « peut-on utiliser le canal de secours p2p pur pour connecter les
replica embarqués avec le serveur principal en cas de défaillance socks ? »

**Non pour l'entrant** : le port média P2P (47471) vit sur le MÊME onion que le
réplica (:80) — quand le descripteur n'est pas servi, les connexions ENTRANTES
vers le téléphone (appels reçus, média, réplica) sont mortes quelle que soit la
voie ; « p2p pur » ne contourne pas un descripteur absent.

**Oui pour le sortant (déjà le cas, renforcé)** : les canaux SORTANTS du
téléphone (client Tor : réplication vers les réplicas, annonces au nœud,
appels émis) fonctionnent même quand son propre service est injoignable —
terrain 23/10 : le téléphone injoignable en direct répliquait et annonçait
correctement (`GET /health OK` sur un autre réplica, annonce fraîche à la
flotte). Le repli opérationnel passe donc par le nœud (miroir de l'état), pas
par un nouveau canal. La console v0.8.9 affiche ce témoin de vie (« VIVANT VIA
LA FLOTTE ») quand la sonde directe échoue alors que l'annonce est fraîche.
