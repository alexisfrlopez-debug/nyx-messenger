journal, « acceptation utilisateur » journalisée chez l'appelé). Ce qui échoue

**téléphone↔réplica de flotte fonctionne TOUJOURS** (journal, /health 375 ms
terrain, offres d'appel livrées).

#### Piste écartée après instruction : les « erreur Tor 513 » HSFETCH

Les exports terrain contiennent des « HSFETCH … erreur Tor 513 — Invalid
argument » (Xiaomi, 22/10 18:49–19:02). **Faux suspect** : ces lignes du ring
buffer proviennent de la **v0.2.38** qui envoyait « HSFETCH <56>.onion »
(suffixe interdit par le control-spec, corrigé en v0.2.39). Preuves : (a) le
message d'échec v0.2.42/43 n'existe pas dans ces fenêtres ; (b) HSFETCH
réussit à 23:06 le même jour après l'auto-mise à jour ; (c) vérifié en
laboratoire : le tor du sandbox **accepte** (250 OK) l'onion terrain nu ;
(d) le checksum prop224 de tous les onions Nyx est valide (script
`check_onion_checksum.py`). Ne pas ré-instruire les 513 des exports vieux de
plusieurs jours : ils appartiennent aux versions dépassées.

#### Conflux = le churn de guards qui étrangle les points d'introduction

Le tor.log du Blackview contient **29 occurrences** de « All current guards
excluded by path restriction type 2 ; using an additional guard » — et le
Xiaomi en montre dès la première seconde après le reset des guards (v0.2.43).
Vérifié dans le source tor 0.4.9.14 (`entrynodes.c` / `conflux_params.c`) :

- `RST_EXCL_LIST = 2` est la restriction créée par
  `guard_create_conflux_restriction()` — **conflux** (circuits multi-chemins).
- `CONFLUX_ENABLED_DEFAULT = 1` : conflux est actif par défaut en 0.4.9.x.
- Le commentaire du code tor lui-même : « This should not happen with 2-leg
  conflux unless there is a race » — or ça arrive en boucle sur les téléphones.
- `ConfluxEnabled` documenté : « conflux … **excludes onion service traffic** »
  — la messagerie Nyx n'émet AUCUN trafic exit (tout est onion↔onion), le
  couper est donc **SANS PERTE fonctionnelle** et retire la source du churn
  qui épuise les guards et perturbe la construction des circuits — dont les
  points d'introduction des services onion des téléphones.

### Correctif 1 — RELAIS MÉDIA PAR LE RÉPLICA (le chemin qui marche toujours)

Nouveau repli « décrochage » : le média d'appel transite par l'onion du
RÉPLICA (port 80 — LE canal prouvé terrain), en complément du direct :

- **Serveur (0.2.36)** — route `GET /call/relay?cid=…&role=caller|callee`
  avec « Upgrade: nyx-pipe » (`relay.go`) : le réplica apparie les deux
  moitiés par cid (16 octets hex échangés E2E dans l'offre) et pipe les
  octets à l'aveugle. Borné : 64 sockets, TTL 240 s pour une moitié jamais
  appariée, coupure nette à 3 h (le cap client est 2 h), un socket par rôle
  et par cid. Gated par le client-auth Tor de l'onion, fermé en maintenance
  (503). Le média reste chiffré E2E (csd CallAudio/CallVideo) — le relais ne
  voit que du ciphertext, exactement le modèle de confiance d'un serveur TURN.
- **App appelante** : l'offre d'appel embarque le champ `relay` (le réplica
  relais choisi par `relayHintFor` — jamais l'onion du pair lui-même, chemin
  mort par définition). À 60 s de direct infructueux, le canal relais est
  ouvert EN PARALLÈLE (le réplica tient chaque moitié jusqu'à l'appariement) ;
  si le direct échoue au terme des 150 s, le HELLO part par le relais.
- **App appelée** : dès l'offre, branchement au réplica indiqué (rôle
  « callee ») ; le HELLO de l'appelant y est authentifié EXACTEMENT comme un
  média direct (signature ed25519 + onion attendu) puis remis à la machine à
  états existante — aucun chemin de confiance nouveau.
- **Direct d'abord** : un appel dont le direct réussit ne consomme jamais le
  relais (la moitié parallèle est libérée immédiatement).
- Compatibilité : le champ `relay` est ignoré par v0.2.43 et avant (extraction
  MiniJson par clé, aucun rejet) ; un émetteur ancien ne l'envoie pas
  (repli simplement désactivé chez le destinataire).

**PRÉREQUIS OPÉRATIONNEL** : le repli ne devient effectif qu'une fois le
**serveur 0.2.36 déployé sur le réplica de flotte** (binaire linux livré dans
le Drive, dossier livrables — déployer par la console comme d'habitude).
Sans déploiement, v0.2.44 se comporte comme v0.2.43 (dégradation gracieuse :
« relais réplica indisponible »).
