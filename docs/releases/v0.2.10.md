# Nyx v0.2.10

## Fix — livraison des messages et demandes de contact (test v0.2.9 sur 2 téléphones)

Retour opérateur après le premier test grandeur nature v0.2.9 sur deux
téléphones : connexion réplica OK (un peu longue), création d'identité OK,
sauvegarde du fichier d'identité OK, ajout de contact OK — mais **rien côté
contact ajouté**, et le **message de test n'est jamais arrivé** sur l'autre
téléphone. Analyse des 5 exports de logs Drive (Blackview XPLORE 1 /
Android 15, Xiaomi 24094RAD4G / Android 16) + code : quatre causes racines
distinctes, toutes corrigées.

## Cause racine n°1 — le destinataire ne pollait JAMAIS son inbox

`pollInbox()` n'était appelé que dans l'écran de conversation (`ChatScreen`,
boucle 10 s). Or pour qu'une conversation existe dans la liste, il faut un
contact — et pour voir les messages d'un inconnu, il faut avoir pollé au
moins une fois. Cercle vicieux : le destinataire sans conversation ouverte
n'a AUCUN chemin de code qui interroge le réplica. Les messages déposés pour
lui restaient dans le journal, indéfiniment.

Correctif : poll global au niveau application (`ServiceLocator.startInboxPolling()`,
30 s, `CoroutineExceptionHandler` dédié). No-op tant que Tor/l'identité ne
sont pas prêts ; se cumule avec le poll fin de l'écran de conversation et un
poll à l'entrée sur la liste. Pas de synchro arrière-plan (le process tué ne
poll plus) — v0.1 assumé, cf. RESTART.md décision 17.

## Cause racine n°2 — l'ajout de contact était purement local

`addContact`/`addContactByAlias` n'écrivaient que dans la base locale :
aucun événement ne partait, le pair ne pouvait rien voir (le type
« contact » existait pourtant côté serveur dans `KnownTypes` depuis v0.1).

Correctif : l'ajout dépose un événement signé type `contact` (body chiffré
sealed box `{"alias":…}` pour le destinataire). À la réception : carte du
contact + message d'information « … vous a ajouté comme contact. ». Si le
réplica est injoignable au moment de l'ajout, `contacts.notifyPending = 1`
(Room v2) mémorise le devoir ; `ensureContactNotified()` le repartage à la
prochaine entrée sur la liste. L'UI indique « demande transmise » ou
« différée ».

## Cause racine n°3 — compteur de séquence en mémoire

Le journal serveur exige `seq = dernier + 1` strictement (rejet « en
attente » / « déjà dépassée »). Le client gardait son compteur en mémoire :
à CHAQUE relance il repartait à 1 et les premiers événements étaient rejetés
par le réplica — messages « envoyés » mais jamais acceptés après un
redémarrage.

Correctif : séquence persistée par auteur (Room v2, table `seq_state`,
migration 1→2) sous Mutex. Dérive résiduelle (restauration de base…) :
auto-réparation dans `postSigned()` — le corps d'erreur du réplica (désormais
inclus dans le message d'exception de `RelayClient.postEvent`) est parsé
(« attendu N » / « dernière N »), la table est recadrée et l'événement
re-signé/redéposé une fois ; HTTP 409 « déjà connu » = succès idempotent.

## Cause racine n°4 — FATAL à la fermeture (logs v0.2.9)

Les exports ont montré 2 `FATAL EXCEPTION:
java.io.InterruptedIOException: read interrupted by close() on another
thread` (02:15:31 et 02:16:16) exactement aux moments où le démon tor
recevait SIGTERM. Cause : le drain de la sortie du démon
(`NyxTorService`, `useLines`) était bloqué dans `readLine()` quand
`process.destroy()` refermait le pipe — exception d'I/O dans une coroutine
déjà annulée = exception non-Cancellation remontée au handler par défaut →
process tué brutalement au lieu de s'arrêter proprement (la fermeture
« propre » de la v0.2.9 fonctionnait mais se terminait par un crash).

Correctif : drain best-effort (`runCatching` — la coupure de flux est le cas
normal d'arrêt) + `CoroutineExceptionHandler` sur les scopes d'infrastructure
(`NyxTorService`, `TorManager`). Une exception résiduelle ne peut plus tuer
le process.

## Constats de test (information)

- Premiers bootstrap tor bloqués ~10 % puis terminés (16 s au 3e essai) ;
  health checks 22–47 s via Tor — circuits lents du réseau, pas d'anomalie
  applicative. La connexion « un peu longue » est le temps de Tor.
- Les exports ne contenaient aucune trace d'envoi de message : l'app ne
  logue pas encore le cycle envoi/réception (à enrichir en v0.2.11 pour le
  diagnostic).
