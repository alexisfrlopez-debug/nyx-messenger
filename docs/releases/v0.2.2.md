# Nyx v0.2.2 — Onion client publié + build « test » à export de logs

> Publiée le 2026-10-15 (session 19). Règle nouvelle : chaque release livre
> DÉSORMAIS DEUX APK — `…-release.apk` (standard) et `…-test.apk` (débogage).
> Installation : télécharger l'APK signé et l'installer par-dessus la version
> précédente (même signature — mise à jour directe).

## 🛠 Serveur — trois correctifs (bugs v0.2.0 n°1-3)

### n°1 — Adresse onion admin instable (dérive à chaque boot)
Le scalaire ed25519 passé à `ADD_ONION ED25519-V3` n'était pas **clampé**
(RFC 8032 : `h[0]&=248; h[31]&=127; h[31]|=64`). Tor traite le blob décodé
comme scalaire brut : selon le contenu du fichier d'identité, l'adresse
publiée dérivait d'un secret non conforme et ne correspondait pas à l'adresse
déclarée — la carte console restait rouge. Le clamp est désormais appliqué à
la dérivation des deux onions (admin et client).

### n°2 — Onion admin autodétruit (service éphémère)
`ADD_ONION` sans `ClientAuth` crée un service **éphémère** : la fermeture de
la connexion de contrôle détruit immédiatement l'onion. v0.2.0 fermait la
connexion après publication — l'adresse admin mourait quelques secondes plus
tard. Désormais la connexion de contrôle est **tenue ouverte** (`Watch()`) et
la republication automatique relance le service si tor redémarre (backoff 5 s).

### n°3 — Onion client jamais publié (API /client/* inaccessible)
Seul l'onion d'ADMIN était publié : l'API client (`/client/*` — alias, inbox,
événements…) restait injoignable via Tor, empêchant tout ajout de contact
depuis l'app mobile. Le serveur publie désormais **aussi** l'onion client
(port 80 → httpPort local), même contrat de maintien que l'admin (Watch +
republication). Les deux services restent actifs tant que le nœud tourne :
deux connexions de contrôle permanentes vers le ControlPort (invariant
vérifiable par `ss -tnp | grep 9051`).

## 📱 Android — nouvelle règle de release : un APK normal + un APK « test »

### Build « test » (variante Gradle `test`, applicationId `net.nyx.messenger.test`)
L'APK test se cohabite avec l'application standard (icône « Nyx TEST ») et
ajoute, en tête de l'écran Conversations, un **gros bouton rouge** :

1. appui → collecte du journal système (`logcat -d -v threadtime`, fin de
   tampon, ~1,5 Mo max) précédé d'un en-tête de diagnostic (version, appareil,
   Android, état du Tor embarqué) — **aucune conversation, aucune clé** ;
2. dépôt direct du fichier `nyx-logs-v<version>-<date>.txt` dans le dossier de
   travail Drive dédié au débogage (Drive API v3, OAuth refresh-token).

L'upload passe **en direct** (hors Tor) : les sorties Tor sont massivement
bloquées par Google, et cette fonction de débogage ne transporte aucune donnée
utilisateur. Le trafic Nyx (chiffré) reste intégralement Tor — inchangé.
Les credentials d'upload sont injectés à la compilation depuis un fichier
git-ignoré (`android/test-upload.properties`) ; sans lui, le bouton affiche
explicitement que le build n'est pas configuré.

L'APK standard, lui, ne contient aucun code de débogage (R8 élimine la branche
`TEST_BUILD`).

## 🔒 Vie privée — inchangée
- Le build test n'expose l'export que par un appui explicite ; rien n'est
  collecté ni envoyé automatiquement.
- Le fichier exporté ne contient aucun message, contact, clé ou champ de
  profil — uniquement des journaux système.
- L'application standard reste strictement identique (Tor embarqué, zéro GMS,
  permissions minimales).

## 📦 Livrables
- `nyx-v0.2.2-<stamp>-release.apk` (versionCode 6) — application standard.
- `nyx-v0.2.2-<stamp>-test.apk` (versionCode 6) — build débogage.
- Les deux : universels (4 ABI, Tor embarqué), signés, zéro dépendance externe.
- Empreintes : `SHA256SUMS-v0.2.2.txt` (à côté des APK) — Releases GitHub +
  Drive `/livrables/dernieres-livrables/`.
