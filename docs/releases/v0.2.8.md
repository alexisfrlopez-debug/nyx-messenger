# Nyx v0.2.8

## Fix — la notification restait bloquée sur « Démarrage de Tor… »

Retour opérateur : la notification permanente affichait « Nyx — Démarrage de
TOR » en continu, même quand Tor était démarré et fonctionnel. Cause lue dans
le code : `NyxTorService.onStartCommand` appelle `startForeground` avec la
notification « Démarrage de Tor… », puis **personne ne met plus jamais la
notification à jour** — `TorManager` connaît l'état réel (StateFlow
`Checking / Starting(pct) / Ready / Failed`, utilisé par l'écran Connexions)
mais aucun chemin de code ne propage cet état vers la notification.

## Correctif

- **`TorManager.setState`** (nouveau, centralisé) : TOUTE transition d'état
  met à jour le StateFlow **et** la notification de premier plan :
  - `Démarrage de Tor…` (0 %),
  - `Connexion Tor… N %` à chaque palier de bootstrap remonté par le control
    port (5, 10, 14 … 100),
  - `Tor actif — trafic anonymisé` (bootstrap 100 %),
  - `Tor en échec — <raison>` (control port injoignable, démon mort, échec de
    lancement/publication — raison tronquée à 90 caractères).
- **`NyxTorService.pushState`** : mise à jour par `NotificationManager.notify`
  sur le même ID (la notification FGS existante est remplacée en place) ;
  garde `foregroundActive` — si `startForeground` a été REFUSÉ (mode dégradé
  v0.2.7, quota FGS épuisé), aucune notification fantôme n'est créée ; canal
  recréé de façon idempotente ; échecs de notify logués (jamais fatals).
- L'icône passe à `stat_sys_download_done` quand Tor est prêt (inchangé).

Le périmètre reste le STATUT TOR (demande explicite) : l'état du réplica
continue d'être affiché sur l'écran Connexions de l'app, pas dans la
notification.

## Contexte serveur (diagnostic indépendant, même journée)

L'export v0.2.7-test (Blackview, 17:28) montre la sonde réplica ENFIN active
(v0.2.7 réparée : `réplicas actifs` renseigné, `GET /health` parti via Tor) —
mais en `SocketTimeoutException: Connect timed out (60 s)`. Sondage indépendant
depuis un client Tor externe : le descripteur de l'oignon data
`5myvqk….onion` est ABSENT des HSDirs (« No more HSDir available to query »,
2 essais à 1 min d'écart) alors qu'un oignon de référence répond — le service
data côté VM est DOWN (nyx-server/tor@default), l'app n'est pas en cause.
Remédiation serveur remise à l'opérateur (redémarrage + journal).
