## 1. VISIO : une image des deux côtés, enfin (demande n°2)

**Cause racine** (preuve 2ᵉ export téléphone 17:24-17:25) : à l'établissement
de la visio MJPEG interop, la **bascule H.264→MJPEG** (`stopCamera` +
`openCamera`) et le **rattachement de l'aperçu UI** (`setPreviewSurface` →
`stopCamera` + `openCamera`) se **couraient** — le `onConfigured` d'une
session déjà morte exécutait `setRepeatingRequest` sur une surface libérée
→ `CaptureRequest contains unconfigured Input/Output Surface!` →
`CameraDevice was already closed` → visio coupée d'office dans les deux
sens (l'appelé ne voyait plus rien alors que le bureau émettait).

**Correctif — `CallVideo` réécrit à trois gardes** :

- **GARDE DE GÉNÉRATION** (`camGen`) : chaque `openCamera`/`stopCamera`
  incrémente un compteur de génération ; les callbacks asynchrones
  (`onOpened`/`onConfigured`/`onDisconnected`/`onError`) d'une ouverture
  PÉRIMÉE sont ignorés — les courses ne configurent plus jamais une
  session morte.
- **RELANCES sur erreurs transitaires** : un échec de configuration sur
  `unconfigured` / `already closed` / `in use` est REJOUÉ une fois 400 ms
  plus tard (×2) AVANT de dégrader la visio.
- **DÉBOUNCE du rattachement d'aperçu** (250 ms, sur le handler caméra) :
  les attach/détach en rafale ne produisent QU'UNE reconfiguration avec
  l'état FINAL des surfaces.

**Miroir micro HS — l'émission seule meurt** (`stopSendingOnly` NOUVEAU) :
une caméra définitivement perdue coupe UNIQUEMENT l'émission locale ; la
RÉCEPTION du flux du pair CONTINUE (décodeur, surface distante et
`feedDecoder` en place). L'overlay affiche « Votre caméra est coupée —
vous recevez toujours la vidéo » (journal « émission visio coupée — la
RÉCEPTION CONTINUE »). Avant, la caméra perdue tuait AUSSI la vue du pair.
La fin d'appel est désormais JOURNALISÉE (« appel terminé (phase) —
motif » — miroir bureau).

## 2. MESSAGES TÉL→PC : notifications + accusés (demande n°3)

**Cause racine** (preuve export bureau 17:24:03 : « HELLO events REFUSÉ de
kxcwah… : signature invalide ») : le **vérificateur** du HELLO P2P
recalculait la chaîne signée avec le **CID (VIDE)** pour le kind
« events », alors que l'émetteur (`P2pClient.pushEvents`) signe le
**COUNT** (nombre d'événements) → TOUT dépôt direct P2P d'événements était
refusé « signature invalide » depuis toujours (repli ADR-017
structurellement mort — les messages n'arrivaient au PC que par le poll,
et l'accusé « delivered » repartait trop tard).

**Correctif** : sélecteur `« call » → cid, « file » ET « events » → count`
des DEUX côtés (`P2pProtocol.helloVerifierString` NOUVEAU — extrait du
serveur pour être TESTÉ, miroir exact des émetteurs). Régression verrouillée
par des vecteurs JVM identiques des deux côtés (`P2pEventsTest` +
`P2pProtocolDesktopTest` : la chaîne de l'ANCIEN code ≠ celle signée).
Côté bureau, les accusés partent désormais DÈS le poll propre et la bulle
plateau ne meurt plus avec une conversation ouverte en arrière-plan
(v0.3.11).

## 3. MÉDIA À VUE LIMITÉE : fermeture MANUELLE (demande n°5)

**Cause racine** : la révélation décrémentait `viewsLeft` (1→0) et
détruisait le fichier AVANT l'affichage — la bulle basculait
IMMÉDIATEMENT sur « média expiré » : le média se refermait de suite,
détruit avant d'être vu.

**Correctif — affichage depuis la MÉMOIRE** (`ChatViewModel.revealMedia`) :
les octets DÉCHIFFRÉS sont chargés AVANT la consommation de la vue ; le
fichier est détruit à la révélation mais l'affichage vit depuis le cache
mémoire DU VIEWMODEL — **jusqu'à la sortie de la conversation**. La
visionneuse plein écran se ferme MANUELLELement (retour), JAMAIS par
minuteur ; l'ordre des branches est corrigé (« révélé » AVANT « expiré ») ;
la carte fichier détruit reste honnête (« affiché, fichier détruit »).
Miroir bureau : `DesktopRepository.revealMediaView` (v0.3.11).
