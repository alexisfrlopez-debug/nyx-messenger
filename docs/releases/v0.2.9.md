# Nyx v0.2.9

## Fix — cycle de vie Tor complet (retour opérateur : trois symptômes liés)

Retour opérateur sur téléphone : (1) la connexion au réplica s'est faite mais
le bouton « Créer mon identité » ne fonctionnait pas ; (2) l'envoi du log a
affiché un message d'erreur ; (3) après fermeture puis relance de l'app, Tor
ne voulait plus se connecter. Demande explicite : « il faudrait pouvoir tuer
le processus TOR proprement en fermeture de l'application dès la première
étape de connexion ».

## Cause racine n°1 — bouton identité inerte

`TorManager.start()` était appelé à CHAQUE entrée sur les écrans Connexions
et Onboarding (`LaunchedEffect`). Il réinitialisait l'état à `Starting(0)`
même quand le démon tournait déjà — et le service, dans sa branche
« déjà en cours » (`alreadyRunning`), ne re-notifiait JAMAIS le manager.
Résultat : état coincé à « Démarrage de Tor… 0 % », `torReady = false`,
sonde réplica jamais relancée, bouton d'identité (gaté sur
`replicaOk = torReady && probe.ok`) désactivé pour toujours. Le commentaire
« idempotent côté service » ne couvrait que le service, pas le manager.

Correctif :
- `TorManager.start()` idempotent : état `Ready`/`Starting` en cours ⇒
  aucun reset d'état ;
- nouveau `reattachRunning()` : le service re-attache le manager au démon
  existant (config conservée, `watchBootstrap` relancé — si tor est déjà
  bootstrappé, l'état repasse `Ready` en un poll).

## Cause racine n°2 — Tor fantôme au relancement

Deux chemins laissaient un démon orphelin tenant le verrou `DataDirectory`
(et les ports) :
- fermeture SANS identité : le bouton retour faisait un `finish()` brut
  (commentaire obsolète « sans identité, aucun service Tor ne tourne » —
  FAUX depuis v0.2.3 : Tor démarre dès l'onboarding) ;
- SIGKILL du process (swipe) : pas de `onDestroy`, tor survivait jusqu'au
  poll de `__OwningControllerProcess` (latence de quelques secondes).

Un nouveau démon lancé pendant la fenêtre mourait immédiatement
(« usually controlled by another process ») → « Tor ne veut plus se
connecter ».

Correctifs (demande opérateur servie : kill propre DÈS LA PREMIÈRE ÉTAPE) :
- sans identité, le retour système quitte via `exitCompletely` →
  **`TorManager.stopNow()`** : arrêt BLOQUANT et borné (SIGTERM → 3 s →
  SIGKILL) — le verrou `DataDirectory` et les ports sont libérés AVANT la
  sortie du processus ;
- `killLeftoverTor()` avant tout nouveau démon : scan `/proc/*/cmdline`
  (`libTor.so`, uid courant) et kill des démons orphelins résiduels ;
- `onDestroy` du service : `killBounded` sur thread dédié (pas de
  `waitFor` sur le thread principal) ;
- `retry()` (bouton Réessayer) s'exécute hors thread UI via
  `stopNow()` + `start()`.
- avec identité : le dialogue « Réduire (Tor actif) / Quitter (tout arrêter)
  » est inchangé.

## Fix — envoi du log

Le build test cible un `folderId` Drive figé à la compilation : le
sous-dossier « Tokens » ayant disparu du Drive (tokens déplacés à la racine
du dossier de travail), l'upload échouait en HTTP 404. Par ailleurs le
refresh token OAuth embarqué a une durée de vie limitée (application de test
Google ≈ 7 jours) : l'envoi Drive n'est pas garanti dans le temps.

Correctifs :
- `test-upload.properties` régénéré : les logs de debug arrivent désormais à
  la racine du dossier de travail Drive ;
- la carte de débogage gagne un recours **« PARTAGER LES LOGS (sans
  Drive) »** (intent `ACTION_SEND`) : toujours disponible, quel que soit
  l'état des credentials — e-mail, fichier, cloud de l'opérateur.

## Rotation du keystore de release

L'ancien `nyx-release.jks` a été perdu avec l'environnement de build (il
vivait dans le dossier Drive « Tokens », supprimé entre-temps). Un nouveau
keystore (RSA-4096, validité 10 000 jours) a été généré et sauvegardé
immédiatement sur le Drive.

⚠️ **v0.2.9 n'est PAS une mise à jour in place** : signature incompatible
avec v0.2.8 → désinstaller l'application avant d'installer v0.2.9 (aucune
donnée utilisateur concernée si aucune identité n'avait été créée).
